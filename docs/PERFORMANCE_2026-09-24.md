# FindHistory 성능 기준선과 최적화 결과

이 문서는 .NET 8 초기 기준선과 .NET 10 재검증 결과를 별도 구간으로 보존합니다. 현재 프로젝트는 .NET 10을 대상으로 합니다.

## .NET 8 초기 기준선 — 2026-09-24

환경: Windows 10.0.26200, .NET 8.0.23, Release 빌드, 로컬 SQLite

## 결론

- SQLite FTS5 trigram 인덱스와 LIKE 폴백을 조합한 하이브리드 검색을 적용했다.
- 100만 건 희귀 검색은 약 8~10배, 결과가 없는 검색은 약 180배 빨라졌다.
- 초기 스캔은 단건 커밋 대신 트랜잭션 배치를 사용해 약 79배 빨라졌다.
- WPF 목록은 명시적인 행/열 가상화와 재활용 모드를 사용한다.
- 현재 측정에서는 Rust 네이티브 모듈이 필요한 병목이 확인되지 않았다.

## 검색 결과

각 수치는 워밍업 후 7회 실행의 중앙값이다. 반환 결과는 최대 1,000개다.

| 데이터 | 시나리오 | 기존 | 최적화 | 변화 |
|---:|---|---:|---:|---:|
| 10만 | 희귀 파일명 | 45.99 ms | 13.89 ms | 3.3배 빠름 |
| 10만 | 경로 + 확장자 | 42.88 ms | 12.74 ms | 3.4배 빠름 |
| 10만 | 결과 없음 | 38.13 ms | 2.35 ms | 16.2배 빠름 |
| 100만 | 최신 1,000개 | 5.86 ms | 4.26 ms | 동급 이상 |
| 100만 | 희귀 파일명 | 579.18 ms | 60.95 ms | 9.5배 빠름 |
| 100만 | 경로 + 확장자 | 649.00 ms | 77.69 ms | 8.4배 빠름 |
| 100만 | 흔한 검색어 | 5.23 ms | 4.74 ms | 동급 이상 |
| 100만 | 결과 없음 | 497.09 ms | 2.76 ms | 180배 빠름 |
| 100만 | 최근 7일 | 4.28 ms | 3.88 ms | 동급 이상 |

FTS가 항상 유리한 것은 아니다. 일치 항목이 1,000개를 넘는 흔한 검색어는 `last_seen_utc` 인덱스를 활용하는 기존 LIKE 경로가 더 빠르므로, 먼저 FTS 선택도를 확인한 뒤 자동으로 검색 경로를 선택한다. 3자 미만 검색어도 기존 LIKE를 사용한다.

## 수집 결과

| 시나리오 | 처리량 |
|---|---:|
| 기존 단건 `UpsertAsync` | 약 114~119 items/sec |
| 배치 `UpsertManyAsync` | 약 9,410~11,971 items/sec |

실제 Windows 최근 항목 폴더 측정:

- 바로가기 1,054개 검사, 251개 유효 항목 해석: 1,278.2 ms
- 해석 속도: 약 825 links/sec
- 251개 SQLite 배치 저장: 31.6 ms

초기 바로가기 해석은 백그라운드 스레드에서 실행하므로 WPF 첫 화면을 막지 않는다.

## 비용

FTS trigram 인덱스는 검색 속도 대신 저장 공간과 대량 삽입 비용을 사용한다.

| 데이터 | 기존 DB | FTS 적용 DB |
|---:|---:|---:|
| 10만 | 34.0 MB | 61.1 MB |
| 100만 | 341.9 MB | 604.0 MB |

100만 건 합성 데이터 생성 시간은 35.35초에서 109.70초로 늘었다. 실제 앱은 최근 항목을 소량씩 기록하고 초기 스캔은 배치 처리하므로 사용자 경로의 병목으로 보지 않는다.

## 앱 프로세스

격리된 임시 DB와 Release 배포본으로 측정했다.

- 시작부터 초기 스캔과 화면 렌더 완료: 약 3,076.9 ms
- 안정 상태 작업 집합: 약 139.2 MB
- 안정 상태 전용 메모리: 약 74.7 MB
- 유휴 5초간 CPU 시간: 0.0 ms

## Rust 도입 판단

현재는 C#과 SQLite 단계에서 목표 성능을 만족한다. 다음 조건이 생기면 Rust 모듈을 다시 검토한다.

- Windows Recent 폴더가 아닌 전체 볼륨을 직접 스캔할 때
- USN Journal 기반 장기 파일 활동 수집기를 구현할 때
- 바로가기/메타데이터 해석을 1초 미만으로 강제해야 할 때
- 해시, 본문 추출, 콘텐츠 인덱싱처럼 CPU 집약 작업을 추가할 때

이 경우 WPF와 설정은 C#에 유지하고, Rust `cdylib` 또는 Named Pipe 사이드카에 수집·파싱·배치 처리만 맡긴다.

## 현재 기준 — .NET 10 재검증, 2026-09-29

환경: Windows 10.0.26200, .NET 10.0.2, Microsoft.Data.Sqlite 10.0.12, Release 빌드

- 10만 건 최신 1,000개: 중앙값 4.43 ms
- 10만 건 희귀 파일명: 중앙값 12.53 ms
- 10만 건 결과 없음: 중앙값 2.09 ms
- 10만 건 `*.pdf` 확장자 와일드카드: 중앙값 6.11 ms, 1,000개 반환
- UI 데이터와 요약 통계 동시 조회: 중앙값 32.72 ms → 14.05 ms
- 10만 개 열기 이벤트의 최근 7일 조회: 중앙값 13.42 ms, 1,000개 반환
- 최근 항목 259개 배치 저장: 27.4 ms
- WPF 실제 기동, 1,085개 바로가기 초기 스캔, 화면 렌더, 비동기 종료 확인

UI 동시 조회 개선은 매 검색마다 `COUNT(*)`와 `SUM(open_count)`로 전체 테이블을 읽던 경로를
SQLite 트리거가 유지하는 1행 `history_stats` 조회로 바꾼 결과다. 또한 DB 작업은 UI 스레드 밖에서
실행하고, 검색 결과 목록은 행마다 추가하지 않고 `ItemsSource`를 한 번 교체하도록 변경했다.
`*.mp4`처럼 정확한 단일 확장자 패턴은 `(extension, last_seen_utc)` 복합 인덱스를 사용하며,
`clip_20??.mp4`처럼 더 일반적인 패턴은 매개변수화된 LIKE 검색으로 처리한다.

날짜별 개별 이벤트 10만 건을 함께 저장한 DB는 82.9 MB로, 파일 집계만 저장했을 때의 65.4 MB보다
약 17.5 MB 증가했다. 이벤트당 약 175바이트 수준이며, 날짜 범위 조회는 `(opened_utc,
recent_item_id)` 인덱스를 사용한다. 이벤트 기록이 추가된 배치 수집은 이 측정에서 약 4,485
items/sec로, Windows Recent의 실제 발생량에는 충분한 여유가 있다.
